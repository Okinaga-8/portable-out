01

先に結論

beta4 INT8 を採用

0.4 MP · 5 秒で base より約 13% 速く、VRAM は 300〜670 MiB 少ない。本番画質（1.0 MP · 10 秒）では差が 2.6% まで縮んで実質互角。速度は理由にならないが、遅くもならない。

サイズではなく形式で選ぶ

11.6 GB の GGUF は 19.53 GiB の INT8 より 1.8〜2.6 倍遅く、VRAM はむしろ増えた。Dynamic VRAM の経路から降りるため。「標準ローダーが読む safetensors か」が唯一の選定基準。

選ぶ理由は作風

同一 seed で SSIM Y 0.699。同じシーンで seed だけ変えた場合が 0.683 なので、モデルを替えるのは seed を替えるのと同じくらい絵が変わる。数字ではなく、出た絵と声で決める話。

採用したファイル

10Eros_Max_h3_TURBO-hybrid_beta4_int8_convrot.safetensors を models/diffusion_models/ へ。標準の「拡散モデルを読み込む」で読めます。GGUF ノードは要りません。

回し方は base と違います。Turbo LoRA を外す・euler / simple・6 step。詳細は 04。

ピーク VRAM の差はテキストエンコーダを再ステージしたかどうかの差で、モデルの性質ではありません（06）。両方とも OOM なし。

beta4 の速度優位は高解像度で縮む

0.4 MP · 5 秒では −13%、1.0 MP · 10 秒では −2.6%、総時間では 401.20 対 403.85 で実質互角。turbo LoRA の 208 patches は 1 ステップあたり固定のオーバーヘッドなので、長いシーケンスのアテンション量に対して相対的に小さくなる、と読めます。

本番画質で beta4 を選ぶ理由は速度ではなく作風です。

step は 6。8 は買わない

作者は「euler/simple 6〜8 step」と言っているので両方測りました（n=3）。

beta4 · 6 step 対 8 step（0.4 MP · 5 秒）
6 step8 step
生成時間（seed 29 / 30 / 31）53.04 / 58.53 / 52.68 秒65.18 / 65.01 / 64.61 秒
s/it5.82〜5.915.85〜5.90
ピーク VRAM14,942〜15,471 MiB14,804〜15,222 MiB

s/it が 6 と 8 で変わらないので、8 step のコストは単純に 2 ステップ分（2 × 5.9 ≈ 11.8 秒）。実測差 +11.9 秒（+22%）と一致します。そして base の 6 step が 55.8〜59.5 秒なので、beta4 を 8 step で回すと base より 10〜16% 遅くなり、選ぶ意味が消えます。

絶対値は信用しない。ペアを信用する

同じ beta4・同じ 6 step でも、セッション内で 49.1 秒の回と 53.0 秒の回があります（±10% 程度は動く）。だから鉄則は「比較する 2 条件を連続して測る」で、絶対秒数を別の日の数字と突き合わせない。07 にその実例があります。

正しく設定できているかは、ログで確かめられる

ComfyUI の起動ログに次の 2 行が出ていれば合っています。

Model MiniMaxH3 prepared for dynamic VRAM loading. 19995MB Staged. 0 patches attached.
[WARNING] unet unexpected: ['adaln_basis', 'adaln_mean']

0 patches attached は turbo LoRA が外れている証拠（base だと 208）。unet unexpected の警告は正常です — beta4 にだけ余分に入っている 2 本のテンソルで、base 側の必要キーは 932 本すべて揃っています（05）。

ワークフローの検査

保存済みワークフローが beta4 として妥当かは機械的に確かめられます。scripts/wf_beta4_check.py は上の表を検査項目として持っています。

python scripts/wf_beta4_check.py WF.json            # 検査だけ
python scripts/wf_beta4_check.py WF.json --fix      # step 数と末尾スラッシュを直す
python scripts/wf_beta4_check.py WF.json --to-beta4 # base 用から WF_beta4.json を作る

--to-beta4 は新しいファイルを書き、元は触りません。保存先の filename_prefix にも _beta4 を足すので、beta4 の出力が base の出力に混ざりません。

filename_prefix の末尾にスラッシュを付けない

付けると連番が進まず、実行するたびに前の出力を上書きします。これで一度、実測を失っています。--fix が自動で落とします。

捨てた道と、撤回した記述

このシートの初版が間違っていた点を、実測で分かった順に残します。同じ間違いを次にしないための節です。

GGUF は「小さいから速い」ではなかった 実測して却下

base（19.53 GiB INT8）対 beta2 ref2va GGUF Q4_K_M（11.6 GB）· 0.4 MP · 5 秒 · 6 step
baseGGUF Q4_K_M

s/it6.1〜6.611.2〜19.3
ピーク VRAM15,098〜15,776 MiB15,873〜15,965 MiB（97.5%）

1.8〜2.6 倍遅く、VRAM はむしろ増えました。決め手はファイルサイズではなく、Dynamic VRAM に乗るかどうかです。

base : Model MiniMaxH3 prepared for dynamic VRAM loading. 19995MB Staged. 208 patches attached.
GGUF : Requested to load MiniMaxH3
       loaded partially; 10957.44 MB usable, 10854.08 MB loaded, 468.31 MB offloaded
  • 19.53 GiB の INT8 が 16 GB で快適に回っていたのは Dynamic VRAM（comfy-aimdo）のおかげ
  • GGUF はその経路に乗らず、ComfyUI 従来の部分ロードに落ちます
  • ファイルを小さくして得たものより、仕組みから降りて失ったもののほうが大きい
  • gguf qtypes: F32 (324), Q4_K (208) — 量子化されているのは 208 テンソルだけ。残り 324 は F32。その 208 は turbo LoRA の対象と完全に同じ集合で、毎ステップ bf16 に展開されます

サーマルではありません（最大 72 C、4080 のスロットリングは 83 C 前後）。未解明：GGUF の実行が回を追って遅くなることがあった（93.7 → 137.3 秒）。ログ上はオフロード量が減っているのに遅い。VRAM 逼迫（余裕 411 MiB）を疑いますが確証はありません。

ここから得た選定基準

候補は「標準ローダーが読む safetensors か」で選ぶ。サイズは二の次。beta4 INT8 はこの基準で選ばれ、実際に 19995MB Staged に乗りました。

beta4 は base とほぼ同型 — だから乗った

scripts/st_probe.py で safetensors のヘッダだけを読んで比較した結果（20 GB のファイルでも数 MB しか読みません）。

base 対 beta4 のヘッダ差分
項目結果

量子化レイアウト同一（I8 × 200 = 17.94 GiB ＋ U8 スケール × 200）

余分な 2 本は diffusers 変換の残骸で、ComfyUI は unet unexpected として無視します。必要なキーが全部揃っているので実害はありません。

撤回：「pruned には Full 向け Turbo LoRA が効かない」「高速化は PDD-Acc のみ」

このシートの初版はそう書いていましたが、この環境の実ファイルには当てはまりません。実測で撤回します。

  • Turbo LoRA の対象は 208 モジュール（blocks.0-49 × attn.qkv_proj / attn.out_proj / mlp.fc1 / mlp.fc2 ＋ token_refiner.blocks.0-1 × 同 4 種）
  • pruned INT8 DiT と 208 / 208 が厳密一致。ミス 0
  • LoRA 内に adaln 系キーは 0 本 → 落ちるものが無い
  • 実行ログの 208 patches attached とも一致

したがって PDD-Acc は「唯一の高速化経路」ではありません。優先度は低いままで構いません。

Turbo LoRA を外すと、映像だけ見ても気づけない

GGUF で LoRA の有無を検証したとき、映像の SSIM Y は 0.662 と「seed 違い程度」でしたが、音は Peak -47.3 dB / Entropy 0.327 と明らかに生焼けでした（LoRA ありは -39.2 / 0.437）。LoRA や step の検証では必ず音も測ること。

06

VRAM の読み方

この環境でいちばん誤解しやすいところ。ピーク VRAM は OOM 接近の指標になりません。

サンプリング中の VRAM（nvidia-smi 20 秒間隔）
条件サンプリング中記録されたピークピークが出る場所
beta4 · 0.4 MP · 5 秒15,1xx〜15,2xx MiB15,252 MiBサンプリング中
beta4 · 1.0 MP · 10 秒13,066〜13,115 MiB（80%）15,238 MiBテキストエンコード時
base · 1.0 MP · 10 秒13,404〜13,476 MiB（82%）14,220 MiBテキストエンコード時

解像度と尺を上げたら、サンプリング中の VRAM が減りました。直感に反しますが理由ははっきりしています。Dynamic VRAM は活性化領域の大きさに合わせて常駐させる重みを減らすので、重い条件ほど重みが VRAM から降りて活性化に場所を譲ります。

ここから出る結論

  • 「0.4 MP で 96.3%」は「高解像度で危ない」を意味しない。仕組みが自動で釣り合いを取る
  • 1.0 MP（ネイティブ上限 0.98 MP = 1344×768 相当）× 10 秒は base も beta4 も OOM なしで完走
  • ピークはテキストエンコーダ（MiniMaxH3TEModel_ 14956MB Staged）を再ステージしたときに出る。DiT の性質ではない
  • したがって W4A8 に期待できた「VRAM の逃げ道」という価値は消えます（08）

この挙動は Dynamic VRAM（comfy-aimdo 0.4.13）が有効な場合の話です。起動ログに DynamicVRAM support detected and enabled が出ていることが前提。GGUF のように別経路に落ちるモデルでは成り立ちません（05）。

07

計測の作法

このシートの数字がなぜ信用できるか、という話。守らないと数字が嘘になる 3 つと、それを機械で担保する道具。

  1. 鉄則 0 — 比較する 2 条件は連続して測る

    絶対値はセッション内でも ±10% 動きます。別の日の数字と突き合わせない。この鉄則を破って一度ハマりました（下記）。

  2. 鉄則 1 — 両側に暖機を 1 本ずつ

    チェックポイントの切り替えには 19.5 GiB のロードが伴います。それを候補側の 1 本目に押し付けると、ありもしない遅さを作ってしまいます。

  3. 鉄則 2 — 音も測る

    映像だけ見ても、LoRA の抜けや step 不足に気づけないことがあります（05）。

このパイプラインは完全に決定的だと確認できた

別々の実行・同一 seed・同一設定の 2 本が SSIM Y = 1.000000。A/B の前提が実測で裏づけられました。差が出たら、それは本当に条件の差です。

実例：アーカイブの数字と比べて、無い問題を作りかけた

beta4 を 1.0 MP · 10 秒で回して 55.5 s/it。アーカイブの Run #10（base、別セッション）が 48.23 s/it だったので「高解像度で beta4 が負けている」と読みました。

実際は違いました。base を同じ条件で連続計測したら 57.0 s/it。beta4 のほうが 2.6% 速い。外れていたのは beta4 ではなくアーカイブの数字のほうでした（当時のほうが 18% 速い理由は不明）。

実例：計測中の手動操作が 1 本を汚した

6 step の 1 本だけ 98.85 秒（他は 53 秒前後）。原因は計測中に手動で 8188 にプロンプトを投げたことで、ログに Cancelling pending prompt が残っていました。

  • s/it は正常のまま（5.92）。壊れるのは wall / reported だけ
  • 絵は無傷 — 汚染された回と再計測の回が SSIM Y 1.000000 で一致
  • ab_run.py は 1 回の実行ログに got prompt が 2 つ以上、または Cancelling pending prompt があれば [!] CONTAMINATED と印字し、JSON にも contaminated として残します

08

見送ったもの

測らずに見送った判断と、その根拠。再浮上する条件も書いておきます。

W4A8（11.68 GiB） 見送り

期待できたメリットと、その行方
期待判定理由
全部が VRAM に載り切って更に速い 唯一生きている ただしステージングが足を引っ張っている証拠がない。19.53 GiB のまま base より速く回っている。「小さくすれば速い」は GGUF で一度否定済み
VRAM に余裕ができて解像度・尺を上げられる 消えた ネイティブ上限 0.98 MP は INT8 のまま到達済み、10 秒尺も実測済みで OOM なし。余らせても行き先がない（06）
ディスク 8 GB の節約 無意味 空きが 578 GB ある

対するコストは、4 bit 重みで満足している絵と声が変わるリスク、別アップローダー（berryber09、本家 TenStrip ではない）、この PC で未検証、検証コスト約 30 分。速度で困っていない状況で 4 bit に賭ける理由がありません。

再浮上する条件：より重い条件（1.0 MP を超える解像度、10 秒を超える尺、参照枚数の増加）で実際に OOM したとき。そのときは 15_download_10eros_beta4.bat の選択 2 で取得し、--plan beta4w4a8 で測ります。

「10Eros」には別系統が 2 つある 混同注意

10Eros-Max は「LTX 2.3・Wan 2.2・Krea 2 から性格を移植した H3 派生」と説明されています。名前に LTX 系の血が入っているのはそのためで、動く土台はあくまで H3 です。

両方 models/diffusion_models/ に置き、標準の「拡散モデルを読み込む」で切り替えます。audio VAE を fp16 に落とさないこと（映像と音がズレます）。

FL2VA / Ref2VA / hybrid

  • FL2VA（first-and-last-frame）— 画像 0 枚なら T2V、1 枚なら I2V、2 枚なら始点＋終点指定
  • Ref2VA（omni-reference）— 画像 9 枚・動画 3 本・音声 3 本まで参照として渡せる。キャラや声を寄せたいとき用。VRAM 的にはこちらが重い

この 2 つは別モデルです。DiT ファイルも別なら Turbo LoRA も別。設計上 Ref2VA は FL2VA より素の画質・音質が落ちます（参照条件付けの対価）。10Eros-Max が謳う「顔の一貫性の向上」はまさにそこに効く可能性があります。

hybrid は、FL2VA をベースに 50 ブロックのうち一部の adaln_proj だけを Ref2VA から取ってくるマージ。1 ファイルで参照モードと t2va の両方を賄えます。beta4 の TURBO-hybrid もこの系譜です。

hybrid を i2v モードで使わないこと

参照（ref2va）形式か t2va 形式で使うもので、i2v モードでは使いません。画像 1 枚を渡す場合も first_frame ではなく参照画像として渡します。ここを間違えると「なぜか品質が出ない」になります。

10Eros-Max の「作風」とは何か

差分として挙がっているのは、静止画的な画風よりも 動きの性格 です。顔の一貫性の向上と弾むような、反応の速いモーション。ダンスなど動きの大きい題材に向く、という評価。逆に、静かなカットで A/B しても差が見えにくい可能性があります。本シートの実測は落ち着いた題材で行っているので、動きの大きい素材ではもっと差が出るかもしれません。
