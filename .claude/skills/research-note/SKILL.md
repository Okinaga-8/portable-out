# リサーチ土台ノート

このリポジトリ(portable-out)は、iPhone から依頼して PC で受け取るドロップボックス。
「まとめて」と言われたときの成果物は、**読んで終わりの要約ではなく、後日ユーザーと二人で
最適解を詰めるための共通の土台**である。この前提が形式を決める。

## 着手前に必ず質問する

ユーザーは思いつきで書くことが多い、と明言している。前提が変わると内容が大きく変わる項目は、
書き始める前に `AskUserQuestion` でまとめて聞く。典型的には:

- 実行環境・バージョン・ハードウェア制約(これで実用的な選択肢が絞れる)
- 「何を作りたいのか」の目標値(尺・規模・品質)
- 情報源が未提示のとき(URL 待ちなど)、待つのか土台を先に作るのか

未提示の URL がある場合は **土台を先に作り、該当セクションをプレースホルダにする**のが既定。
その節には「動画は再生できない/字幕が非公開だと取得できない」など、こちらの制約も明記する。

## 必ず入れる要素

1. **用語の整理と訂正** — ユーザーの言葉が正しければ「正しい」と明言する。
   誤りだけでなく、**曖昧な一語を複数の別問題に分解する**のがいちばん効く
   (例: 「結合」→ 生成段の継続 / 編集段の遷移 / 出力段の連結)。
   どこに労力の大半があるかを示す。
2. **確度の表記** — 全事実に付ける。
   `一次`(README・公式 PR 番号など出所が特定できる) /
   `一致`(複数の二次情報が一致) / `要検証`(単一記事、または自分の推論)。
   **自分の推論は必ず「要検証」に落とし、推論だと明記する。**
3. **調査の限界** — 到達できなかった一次情報(egress ブロック等)を隠さず書き、
   「PC 側で最初に開くべきリンク」として先頭付近に置く。
4. **選択肢の比較表** — 弱いものから強いものへ並べ、各行に「解決すること」と
   「残る問題」を必ず書く。どれを推すかは根拠付きで述べる(仮説なら仮説と書く)。
5. **検算できるものは検算する** — 出典の数値どうしの整合を自分で確かめて示すと、
   情報の信頼度がユーザー自身で判断できるようになる。
6. **最小実験** — 今夕/次の作業で手が動く粒度。順番に意味を持たせ、
   各実験に「記録するチェックリスト」を付ける。結果をどう報告すればよいかも書く。
7. **未解決の論点** — 次回一緒に詰める問い。実験で決着するものと調べ直しが要るものを分ける。
8. **出典** — 一次 / 未取得 / 二次 に分けて列挙。
   出所不明の SEO サイトは「数値の根拠にしていない」と明示して警告する。

## 形式

- `docs/<topic>.html` に **単体で開ける完全な HTML**(doctype / head / body 込み)を置く。
- 同じ内容を Artifact でも公開し、リンクを返す(PC で開くのが一番速い経路)。
  Artifact 用のファイルは doctype を含めない形式なので、`<!--HEADEND-->` を目印にして
  head 側と body 側を分割し、1 つの原稿から両方を生成すると二重管理にならない。
- 書く前に `artifact-design` スキルを読む。長文なので、広い画面では sticky の目次を付ける。
- 日本語で書く。ライト/ダーク両テーマを CSS 変数で必ず対応させる。
- README の「成果物」表に 1 行追加する。

## 更新するとき

同じテーマの続報(実験結果・URL 到着)は**新規ファイルを作らず既存ファイルを更新**し、
Artifact も同じパスで再公開して URL を保つ。文末の「次回の更新予定」を書き換える。
